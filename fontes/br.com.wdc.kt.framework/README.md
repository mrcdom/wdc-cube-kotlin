# Framework

Reusable base libraries, independent of the WDC Store application.

## Modules

- [br.com.wdc.kt.framework.commons/](br.com.wdc.kt.framework.commons/) — Utilities and base types (KMP)
- [br.com.wdc.kt.framework.cube/](br.com.wdc.kt.framework.cube/) — Cube MVP engine (KMP)
- [br.com.wdc.kt.framework.domain/](br.com.wdc.kt.framework.domain/) — Data access contracts: repository, criteria, projection, transaction (KMP)
- [br.com.wdc.kt.framework.persistence/](br.com.wdc.kt.framework.persistence/) — Transactions over JDBC and remote transaction coordinator (JVM)
- [br.com.wdc.kt.framework.jooq/](br.com.wdc.kt.framework.jooq/) — Declarative queries over jOOQ, for H2 and PostgreSQL (JVM)
- [br.com.wdc.kt.framework.rest/](br.com.wdc.kt.framework.rest/) — REST APIs over Javalin: routes, security, errors, per-request context and transaction, OpenAPI (JVM)
- [br.com.wdc.kt.framework.cube.remote/](br.com.wdc.kt.framework.cube.remote/) — Remote Cube: the presenters on a server, the views in a client, over a protocol free of UI and web technology. The host (JVM) and its Javalin routes; the client in Kotlin/JS and in TypeScript, each with React bindings of its own

## Using as a dependency

The Kotlin modules are published on Maven Central (the four `framework-cube-remote-*` from 0.5.0), under the [MIT](LICENSE) license, in the group `io.github.mrcdom.wdc.kt`. All ship with the same version.

Targets: JVM (Java 21), Android (minSdk 26), JS, WasmJS, iosArm64 and iosSimulatorArm64. 0.4.0 is compiled with Kotlin 2.4.21 (0.2.0 and 0.3.0 with Kotlin 2.3): consumers on the JS, WasmJS and iOS targets need a Kotlin at least as new as the one the version was compiled with.

```kotlin
// build.gradle.kts of a Kotlin Multiplatform project
kotlin {
    sourceSets {
        commonMain.dependencies {
            implementation("io.github.mrcdom.wdc.kt:framework-cube:0.4.0")   // navigation and presenters
            implementation("io.github.mrcdom.wdc.kt:framework-domain:0.4.0") // data access contracts
        }
    }
}

// build.gradle.kts of a JVM server module
dependencies {
    implementation("io.github.mrcdom.wdc.kt:framework-jooq:0.4.0") // already brings persistence and domain
    implementation("io.github.mrcdom.wdc.kt:framework-rest:0.4.0") // REST API over Javalin
}
```

## 0.5.0 release notes

Not yet published. Fixes defects found while reviewing a port of the architecture to another language.

| Module | Change | Breaking? | What to do |
|---|---|---|---|
| `framework-cube-remote-backend`, `framework-cube-remote-backend-javalin` | **New modules**: the remote Cube backend, extracted from the WDC Store's remote view (the Java version's `remote.backend`), with its Javalin routes apart. An application implements `RemoteApplication` and holds a `RemoteApplicationSupport` (views, protocol, signed history, life), given the vid of each scope class; a `RemoteApplicationRegistry` keeps the sessions, releases the expired ones (`startCleanup`) and pushes changes made outside a client message (`startFlushing`). In `-backend-javalin`, `DispatcherController.configure(config, registry)` and `IndexHtmlController.configure(config, vararg contexts)` add the routes (the session cookies also on `/<context>/index.html`). | New | See the modules' READMEs; the WDC Store's `RemoteRootPresenter` is a complete example. |
| `framework-cube-remote-backend` | **Several instances:** `RemoteApplicationRegistry.onCreated(listener)` tells of each session the registry makes, and `releaseIdle(id)` releases a session that has no socket (its tab went on elsewhere). An application served by several instances passes the first to the others and calls the second when told; the WDC Store's backend does, over its instances' mesh. **Metrics:** `onMessage(listener)` tells, after each client message, how long it took and whether it failed; the transport reports it (`messageHandled`, which `DispatcherHandler` calls). The framework has no metrics library; the WDC Store's backend records them in Micrometer. | New | Nothing, unless the application runs on several instances or wants metrics. |
| `framework-cube-remote-bridge`, `framework-cube-remote-bridge-react` | **New modules**: the client of the remote backend in Kotlin/JS (the Java version's TeaVM bridge), with no UI technology — `RemoteBridge` (session, handshake, WebSocket, history, form data and events), `RemoteScope` (a scope read by name) — and its React bindings with kotlin-wrappers (`RemoteViews`, `useView`, `useHold`, `remoteView`). The TypeScript client is split the same way: `wdc-cube-remote-bridge` and `wdc-cube-remote-bridge-react` (on npm; see below). | New | See the modules' READMEs; the WDC Store's `remote.react.kotlin` is a complete example. |
| All | **The public API is checked and documented.** Each module keeps its API in `api/` (Kotlin ABI validation; `check` fails on an unrecorded change, `updateKotlinAbi` records it), and its javadoc jar carries the Dokka documentation (it was empty). | No | See "The public API" below. |
| `framework-cube-remote-backend`, both bridges | **Security, compared with the WDC Store's remote view before 0.5.0 (and the Java version):** the handshake was textbook RSA (no padding, a ~250-bit key from the `app_skey` cookie), the session ids and addresses were signed with RSA-512 and MD5, the servers fell back to fixed development keys, and AES-GCM used one IV for the whole session. Now each connection agrees on its key by **ECDH P-256 + HKDF-SHA256** (`clientKey` in the first message, `serverKey` in the answer; forward secrecy), every ciphered value carries its own random IV, and the server signs with **HMAC-SHA256** (`RemoteAppSecurity`: a random key per process, or `useKey` for several instances). The only cookie is `app_id`. | **Yes** (wire) | A client of the protocol does the ECDH handshake; both bridges do. |
| `framework-rest` | **CORS of its own**, in place of Javalin's plugin (also as `Cors.install(config) { … }` for a server without a `RestApi`). The plugin answered **400** to any request with an `Origin` not listed, including the server's own pages on another host or port (browsers send `Origin` on module scripts and POSTs) — a backend outside the listed ports could not serve its own pages. Now a same-origin request passes untouched and an origin not allowed gets no CORS headers, as the CORS specification has it. Origins with a scheme of their own and no port (`tauri://localhost`) and `*.` subdomains are accepted. | Behavior | Nothing, unless something relied on the 400: the browser still hides the answer from a page on an origin not allowed. |
| `framework-cube` | **An application's actions run one at a time** (`CubeApplication.runAction`, used by the guard of `action`/`actionOf`/`actionOf2`): one that starts while another waits on I/O waits for it, without blocking a thread; an action that runs another runs it at once (the lock goes with the coroutine context). With blocking I/O this held by itself; with suspending I/O it is what keeps two clicks from interleaving. | Behavior | Nothing, unless an action waits for another action started in a coroutine that is not its own (it would wait for itself): call it directly. |
| TypeScript bridges | **On npm**: `wdc-cube-remote-bridge` and `wdc-cube-remote-bridge-react` (they were `@wdc/remote-bridge` and `@wdc/remote-bridge-react`, imported from source only), built as ES modules with their types, published by the `publish-npm.yml` workflow with trusted publishing. Importing the React package no longer makes the coordinator: it is made on first use, in the browser. | **Yes** (names) | `npm install wdc-cube-remote-bridge-react wdc-cube-remote-bridge`; a shell that imported `@wdc/…` from source renames its imports and aliases. |
| `framework-cube-remote-backend`, both bridges | **The remote protocol is versioned (1)**: the client sends `protocol` in the handshake, the host answers with its own; a handshake with another version or none, and any message before an accepted handshake, get `{"error": "unsupported-protocol", "protocols": [1]}` and are not read (`RemoteProtocol`). The client then stops and says the page is out of date. Also fixed in both bridges: requests queued before the handshake went out right after the hello, not after its answer. The protocol is specified, with **shared conformance fixtures** for hosts and clients, in `conformance/` of the remote framework. | **Yes** (wire) | A client of the protocol sends `protocol: 1` with its `clientKey`, and waits for the answer before sending anything else; both bridges do. |
| `framework-commons` | **`RSA` removed** (and its JVM `RSA.generate`). It was textbook RSA — `mᵉ mod n`, no padding —, which is not safe to cipher anything with; the remote protocol, its last user, now agrees on a key by ECDH (above). | **Yes** | Use the platform's cryptography: RSA-OAEP from the JCA or Web Crypto, or a key agreement (ECDH) as the remote protocol does. |
| `framework-domain` | **Security.** `Criterion.restore` (reading the criterion that comes from the wire) refuses with `InvalidRequestException` (400) a number of values the operator does not accept (`BETWEEN` with one, `EQ` with none, `GT` with two) and `null` in an ordering comparison, `LIKE`, `ILIKE` or `BETWEEN`. Before, the predicate was kept, the field counted as set and the translator dropped it from the SQL: a `delete` "with criterion" became a `DELETE` without `WHERE`, and `count`, `fetch` and the per-user scope lost the filter. `EQ`/`NE` with `null` and empty `IN` are still accepted. | Behavior | None, unless a client sent malformed predicates: it now gets 400. |
| `framework-jooq` | `CriterionTranslator` refuses (`IllegalArgumentException`) a predicate whose operator and values disagree, instead of discarding it. | Behavior | A criterion built in code only gets there through `restore`; nothing to do. |
| `framework-cube` | **Navigation requested during another one.** `execute()` decides, no longer `navigate()`: requested from inside the current one (the presenter, in `applyParameters`) it is a redirect and interrupts it, as before; requested from outside (view action, history) it **waits** for the current one to finish. Only the last request waits; an earlier one, or one that was waiting for a navigation that failed, returns `false`. The module now depends on `kotlinx-coroutines-core`. | Behavior | Nothing, unless a presenter launches another coroutine to navigate and waits for it inside `applyParameters` (it would wait for itself): navigate directly. |
| `framework-cube` | With `false` in `applyParameters`, the current place is that of the presenter that stopped the composition, not the last step of the route (never visited). | Behavior | Nothing. |
| `framework-cube` | **`Scope`** replaces the `ViewState` interface and the `ViewState.toJson` extension (`ViewStateExt.kt`): one abstract class with what a presenter shows. `toJson(instanceId, viewIdOf = null)` is a member. Its fields (`var x by field(initial)`) ask for a repaint when assigned a different value; the presenter binds it with `bind(scope)` (in `AbstractPresenter`) and no longer calls `update()` after each change. A change inside an object already assigned is not seen: assign a copy or call `changed()`. | **Yes** | Rename `XxxViewState : ViewState` to `XxxScope : Scope()` (a class now: add the parentheses); `toJson(id)` is now a member, so drop the import of the extension. Declare the fields with `field(...)`, wrap the scope in `bind(...)` and drop the `update()` calls that follow a field assignment. |
| `framework-cube` | **A scope writes itself as JSON**, with no code per scope: `write(instanceId, json, viewIdOf)` is now `open`, with a default that walks the fields declared with `field(...)` (registered as they are declared) in declaration order, after `"id"`. `null` and blank strings are left out; numbers and booleans always go; a field holding a `Scope` goes as `"<name>ViewId"` (the instance id `viewIdOf(scope)` gives), a list declared with the new `scopes()` as `"<name>ViewIds"` (empty included) — both only when `viewIdOf` is given; lists, maps, enums, `Externalizable` and the new **`ScopeValue`** (a struct that writes itself as one JSON value) as themselves; any other type fails naming the field. `field(initial, sent = false)` keeps a field out (a typed password); plain `var`s (the actions) never go. | **Yes** | Delete the hand-written `write` overrides that these rules cover (keep one only for a shape they can't give); make the structs your scopes hold implement `ScopeValue`; declare with `sent = false` what must not reach the client; where a scope is written for a remote view, pass as `viewIdOf` a function that gives the instance id of the view that draws a nested scope (the remote host's own registry). |
| `framework-cube` | **Actions are fields of the scope**: `Action`, `ActionOf<T>`, `ActionOf2<T, U>` (`suspend operator fun invoke`; `Action.NOOP`, `ActionOf.noop()`, `ActionOf2.noop()` until bound). The presenter binds them once, in its constructor, with `action { }`, `actionOf { }` or `actionOf2 { }` (`AbstractPresenter`), which **guard** them: a failure the body did not handle goes to `onActionFailure` → `CubeApplication.alertUnexpectedError` (new, logs by default; the WDC Store shows "Unexpected error: <cause>"), and `app.updateHistory()` runs after every action. For remote views an action takes an **event code** and **`FormParam`**s (`actionOf(2, FormParam.int("p.quantity")) { … }`, optional `target` scope); `Scope.dispatch(code, formData)` runs it (an unknown code is an error, a code bound twice fails), `scope.onSync { }` / `Scope.sync(formData)` copy what the user typed, and `onEvent(code) { }` handles a code by hand. | **Yes** | Turn each public `onXxx` of a presenter into a field of its scope bound in the constructor (`scope.onBuy = action(1) { buy() }`, the body private); views call `scope.onXxx(...)` inside `safeCall`/`safeAction`. Drop the per-presenter `try/catch` → `alertUnexpectedError` and the `updateHistory()` after actions. Move the event-code `when` of remote views into the bindings. |
| `framework-cube` | **Presenters no longer create views.** `ScopeSlot` (`setScope(scope?)`) replaces `CubeViewSlot`, and `CubeIntent.setScopeSlot`/`getScopeSlot` replace `setViewSlot`/`getViewSlot`: a presenter hands its scope to the parent, which keeps it in a field of its own scope. Each rendering technology owns its views (next row). `AbstractCubePresenter` no longer holds a view: its `view` field, `view()` and `update()` are gone. | **Yes** | Remove the `createView` factories from the presenters and their registration from every entry point; register each view once in the view layer. Views take the scope (and, where needed, the application) instead of the presenter. Replace `CubeViewSlot { v -> … }` with `ScopeSlot { s -> … }` and `setView(view)` with `setScope(scope)`. |
| `framework-cube` | **The framework knows only scopes.** The `CubeView` interface is gone, and the framework keeps no view, registry or view lifecycle: drawing a scope, and letting go of what drew it, is up to each rendering technology. `Scope` gets one **updater** — `setUpdater(updater)`, installed by what starts drawing the scope; `clearUpdater(updater)`, which takes it back only if it is still the same instance; `changed()`, which calls it for a change inside an object already assigned — and a scope with no updater just keeps its values. A nested scope is the slot: a scope leaves the screen when it leaves its parent's field, which repaints the parent's view, and the technology releases the child's view there. `AbstractCubePresenter.release()` no longer releases a view; presenters never release views. | **Yes** | In each rendering technology, keep a catalog (scope class → view) and the live views, create a view the first time a parent's drawing asks for a scope's, install its updater (`scope.setUpdater`), and release the views a drawing no longer asks for (`clearUpdater` with the same function). In Compose or React, make each view a function of its scope that installs itself as the updater while it draws and takes it back when it leaves the screen (the WDC Store's `useScope`). Replace the presenter's `update()` with `scope.changed()`. |
| `framework-cube` | **`commitComputedState` runs from the application.** `CubeApplication.commitComputedState()` runs every live presenter's (`PresenterBase.commitComputedState`, default empty); each view layer's scheduler calls it once per paint cycle, before it picks the dirty views (what it changes joins the same cycle). | **Yes** | Call `app.commitComputedState()` in your view layer's flush, once, before painting; remove the per-view `prepareForPaint`/`updateMuted` that called each presenter's. |
| `framework-cube` | **Segments replace child presenters.** A piece of the screen without navigation of its own (a panel, a list row) is a smaller scope that the owner creates and keeps in a field of its own scope (or in a list declared with `scopes()`), with a view of its own and no presenter: a change repaints its own view. Actions bind to it with `target = segment`. A segment that leaves the screen (a removed cart row) is just taken out of the field or list. `AbstractChildPresenter` is gone; `AbstractCubePresenter` now extends the new `AbstractPresenter`. | **Yes** | Turn each child presenter into a segment of its owner's scope: create its scope in the owner (`private val panel = PanelScope()`), move its loading and actions into the owner (`actionOf(1, …, target = panel) { … }`), and keep it in a field of the owner's scope. |
| `framework-cube` | **`CubeTreePlace` and `CubeKeys`**: a place that knows its parent (`CubeTreePlace.ROOT`, the application itself — no presenter, id -1, not a step of any path —, `ROOT.child(name, factory)` for a top-level place and `place.child(name, factory)` below it; ids grow from the top to the leaves), and a base for the application's keys classes (the application, the intent — a new one from the current state when none is given — and `flip()`). Each keys class declares its place in its companion, from the place of the keys it extends, so the class tree is the place tree. `CubeApplication.flip(place, intent)` navigates through the path of the place. | No | Optional: declare each place in its keys class and navigate with `XxxKeys(app).flip()`, instead of an enum of places and one navigation function per place. |
| `framework-cube` | **`CubeApplication.applyParameters(intent, initialization, deepest)`**: the application, root of the place tree, takes part in every navigation before the first step, in the redirect-marked context (a navigation requested in there is a redirect). `initialization` is `true` only the first time; `deepest` is `true` when there are no steps (`flip(CubeTreePlace.ROOT)`); `false` stops the navigation at the root. On rollback it runs first, with the source intent (`false, false`). The default returns `true`. | No | Optional: move a root presenter's job (page frame, session restore, the first level's slot) into the application and declare the root keys with `CubeTreePlace.ROOT`. |
| `framework-cube` | **Addresses resolved by the framework**: `CubeApplication(places)` takes the places an address can name (listed by hand, which also creates them before the first navigation; a repeated name or the root is refused), and `flip(address)` / `flip(intent)` navigate to the place named, through `placeOf(name)` — an unknown name goes to `CubeTreePlace.ROOT`. | No | Optional: pass the list to the constructor and drop your own name-to-place map. |
| `framework-domain` | **Resource calls**, package `resource`: one operation of the presentation on the data per class, named by its verb, in the spirit of the HTTP methods — `ResourceQuery` (GET; no transaction of its own), and the closed write verbs `ResourceCreate` (POST), `ResourceSave` (PUT), `ResourceUpdate` (PATCH) and `ResourceDelete` (DELETE), whose final `run()` opens `required` on the `TransactionService` a function given to the constructor returns (called when it runs; without one, the write runs directly). What fits no verb extends `ResourceCall`. The request is the constructor's named parameters, a new instance per use: `ProductQuery(productId = id).run()`. See the [module README](br.com.wdc.kt.framework.domain/README.md#resource-calls). | No | Optional: replace the presentation's service classes with one call per operation. |
| `framework-domain` + `framework-persistence` + `framework-rest` | Unknown or expired remote transaction: `RemoteTransactionNotFoundException` (was `TransactionSystemException`), 410 in REST. In use by another request: `TransactionConflictException` (409; was `TransactionSystemException`, 500). | **Yes** (type) | Whoever caught `TransactionSystemException` for these cases catches the new types. |
| `framework-persistence` | A rollback requested while a request is using the transaction takes effect at once (outcome recorded, the `txId` accepts no more requests), but the connection only closes when the request unbinds it; a commit at that moment is `TransactionConflictException`. `suspend` always unbinds the thread. Committing a transaction marked for rollback rolls it back and throws `TransactionConflictException`, instead of answering success. `begin(ownerKey, quotaKey)` counts the cap by `quotaKey` (interface default: falls back to `begin(ownerKey)`). | Behavior | Implementers of `RemoteTransactionCoordinator` may override `begin(ownerKey, quotaKey)`. |
| `framework-rest` | With `X-Tx-Id`, the request runs as a participant (`service.required`): if it fails midway, the remote transaction is condemned and the client's commit answers 409. `ownerKey` becomes `user:<id>/client:<X-Client-Id>`, and the new `quotaKey` (`user:<id>`) keeps the cap per user. | Behavior | Whoever overrode `ownerKey` checks whether they also want `quotaKey`. |
| `framework-domain` + `framework-persistence` | **A participant that fails dooms the transaction and the owner throws.** When a block that joined the current transaction (`required`, `mandatory`, `supports`) throws and its caller catches the exception and carries on, the owner still rolls back, as before, but now throws `TransactionSystemException` ("The transaction was rolled back: a call inside it failed.") instead of returning the block's result. An explicit `setRollbackOnly()` still rolls back without throwing; `isRollbackOnly()` is `true` in both cases. | Behavior | Code that caught a nested failure and expected the outer block to return normally now gets the exception: let it propagate, or use `requiresNew` for a step that may fail on its own. |
| `framework-persistence` | `RemoteTransactionCoordinatorImpl.startReaper(executor)` sweeps expired remote transactions periodically (`RemoteTransactionOptions.reapIntervalMs`, `reapIntervalSeconds` in the configuration, 15 s by default); `reapExpired()` is public. Before, the sweep only ran on `begin`: on a quiet server, an abandoned transaction kept its connection and row locks past the timeouts. | No | Call `startReaper` once at startup with a `ScheduledExecutorService` you already have, and close the handle at shutdown. |
| `framework-rest` | `commit`, `rollback` and `status` of the remote transaction without the `X-Tx-Id` header answer 400 (`InvalidRequestException`), not 403: the request is malformed, access was not refused. A foreign owner is still 403. | Behavior | A client that told the cases apart by the status checks 400. |
| `framework-rest` | **Queries have a cap**: `RepositoryRpc.maxLimit` (1000 by default, `null` turns it off). `fetch` with `limit` above it, `fetch-page` with `pageSize` outside `1..maxLimit`, and a `fetch` without `limit` that would bring more rows answer 400 — refused, not cut short. Before, `limit` had no ceiling and a missing one brought the whole table. | Behavior | A client that read more than 1000 rows at once pages the query, or the application raises `maxLimit`. |
| `framework-rest` | **`scope` also guards `update`.** Before `beforeUpdate`, `RepositoryRpc` counts the target row with the key plus `scope`; outside the caller's reach, `NotFoundException` (404 — the same answer as a row that doesn't exist, so the refusal doesn't tell the row is there); without the key, 400. Before, the reach of an update depended entirely on `beforeUpdate`. Without a `scope` set, nothing changes (no extra query). With a data policy (`rpc.policy`), `scope` is not consulted and the policy decides: 404 or 403 by whether the caller reads the row. | Behavior | An application that checked ownership in `beforeUpdate` can drop that check; keep only what the scope cannot see (reassigning the owner). |
| `framework-rest` | **Reads join the client's remote transaction.** With `X-Tx-Id`, the `RepositoryRpc` reads (`count`, `fetch`, `fetch-page`, `fetch-by-id`, `GET {id}`) run in it as participants, through the new `RestCall.inRemoteTransaction` / `RestTransactions.joinRemote`: they see the transaction's own writes and are not blocked by its row locks (on SQL Server without RCSI, a read of a row the transaction locked waited for the lock timeout). Without the header, nothing changes. | Behavior | A client that relied on reads inside a remote transaction seeing only committed data reads with `notSupported` (no header). |
| `framework-rest` | The KDoc of `RepositoryRpc.scope` (and the README) warns: add the scope with `field.and().eq(owner)`, never just `eq`. On a field the client marked with `"or": true`, `eq` becomes one more alternative and the scope is gone. | No | Check your `scope`s: replace `eq(owner)` with `and().eq(owner)`. |
| `framework-domain` | **Security.** `CriterionCodec` refuses (400) a value that is not the JSON `null` but that the reader turns into `null` — `""` for a number. It became `IS NULL`/`IS NOT NULL`, and `NE [""]` in a `delete` wiped the table. Only the JSON `null` is a null operand. | Behavior | A client that sent `""` to mean "no value" gets 400; send `null`. |

## Publishing

The configuration is in [`fontes/build.gradle.kts`](../build.gradle.kts) (the `publishedModules` block), with the `com.vanniktech.maven.publish` plugin. There is a single version, defined there.

```bash
cd fontes

# Check the artifacts locally (~/.m2), unsigned
./gradlew publishToMavenLocal

# Send to Maven Central (requires credentials and a GPG key in ~/.gradle/gradle.properties)
./gradlew publishToMavenCentral
```

Both tasks exist only in the published modules. Sending creates a *deployment* on the [Central Portal](https://central.sonatype.com/publishing/deployments) that must be released manually. A released version cannot be changed or removed.

### The npm packages

The remote bridge's TypeScript client goes to npmjs.com with the same version: `wdc-cube-remote-bridge` and `wdc-cube-remote-bridge-react` (their `package.json`, in [`br.com.wdc.kt.framework.cube.remote/`](br.com.wdc.kt.framework.cube.remote/)). The workflow [`publish-npm.yml`](../../.github/workflows/publish-npm.yml) publishes them on the version tag (`vX.Y.Z`), or by hand: it tests and builds them, installs the packed packages into another project (`scripts/verify-npm.mjs`, which the CI also runs on every push), publishes the core and then the React package, and asks the registry until both are visible (`scripts/check-published.mjs`).

There is no token: npm's **trusted publishing** takes the workflow's GitHub identity, and adds provenance. On npmjs.com, each package names this repository and the file `publish-npm.yml` under *Settings → Trusted Publisher*. If npm does not let a trusted publisher be named for a package that does not exist yet, the first version goes out by hand (`npm login`, then `npm publish --access public` in each package's folder, the core first), and the workflow publishes the next ones. Before tagging: the version in both `package.json` files is the framework's.

### The public API

Each published module keeps its public API in an `api/` folder (a dump per platform, by the Kotlin Gradle plugin's ABI validation). `./gradlew check` (and so `build`) fails when the code's API differs from the dump. A change to the API is then a decision, not an accident: run `./gradlew updateKotlinAbi`, look at the diff, and commit it with the change — a removed or changed signature is a breaking change for the release notes.

The API documentation comes from the KDoc, by [Dokka](https://kotl.in/dokka): `./gradlew dokkaGeneratePublicationHtml` writes it to each module's `build/dokka/html`, and it is published as the module's javadoc jar.
